## 仕様を最初から良くするために

| 仕様 | ラウンド | 最初に足りなかった問い | 次から |
| --- | --- | --- | --- |
| 写す先の pre-push がこのリポのものか | 3 | 「その判定に要る情報は、プラットフォームのどこにあるか」(共有の `hooks/` のファイルには持ち主の情報が無い) | 中身から持ち主を推定する判定 (文字列、履歴の blob) は、推定の材料の次元 (ブランチ・detached HEAD・stash・shallow・利用者による編集) ごとに外れる。判定に要る情報がプラットフォームに無ければ推定せず、違えば止めて人に渡す |

判定の作り直しは次の順に進んだ。

1. `grep PUSH_OK` (tools の形)。拒否メッセージの案内どおり利用者が自分の hook に PUSH_OK の検査を足すと、次の verify.sh がその hook を黙って上書きする。
2. HEAD の履歴にある版の blob との一致。別ブランチで写した版を、その版を持たない worktree が別の hook として落とす。
3. 全ての ref の、単純化しない履歴。他の worktree の detached HEAD にだけある版を取りこぼし、stash した編集を版に含める。
4. 推定をやめ、違えば旧版でも落として置き換えのコマンドを示す (`1496e58`)。

findings.md の回数の規則 (3 回目で機構の種類を変える) が、4 で止める根拠になった。旧版の自動の写し直しをやめる判断は、issue の挙動を変えるのでユーザーに選んでもらった。

## 良かったこと

- コミット前の自分のレビューで、テストの `git commit -am` が作業ツリーと HEAD が同じとき (コミット後の CI) に「nothing to commit」で止まる不具合を見つけた。差分ではなく、コミットした後の状態でテストが通るかを問うと見える。
- テストの所要時間が約 9 分から約 9 秒になった。verify.sh を回す clone の 1 つに shellcheck が落ちるファイルが無く、検査一式を入れ子で回していたのが原因だった。
- 負のプローブ (判定を常に真にする、旧い判定に戻す) を、修正のたびに subagent に回させた。テストがその修正を固定していることを毎回確かめられた。
- 指摘を出した担当は sonnet の定義域・原因の深さと、haiku の自然言語・定義域 (stat の方言) だった。haiku の多くの担当は指摘なしで、文面の担当の書き換え案 (記号への圧縮、代案の否定の誤適用) は観点の判定規則で却下できた。

## 直したこと

| 問題 | 直した先 |
| --- | --- |
| 写す先の pre-push を中身から「このリポのもの」と推定して上書きしていた | 推定をやめ、無ければ写し、同じなら何もせず、違えば上書きせず落ちて置き換えのコマンドを示す (`f061742` → `f76d5e5` → `1496e58`) |
| テストの mode の比較に `stat -f %Lp` (BSD) を使い、GNU stat の CI で比較が壊れる | 実行可能かどうかの比較にした (`e87ccf2`) |
| CI の shellcheck が SC2015 (`A && B \|\| C`) で落ちた。手元の 0.11.0 では出ない | `{ ...; }` でまとめた (`f94576f`) |
| watch が Codex の Completed を拾わず、約 1 時間待った | `@codex review` を手で出した。原因と残りは下 |

watch が拾わなかった経緯:

1. 1 回目の watch は、CI の失敗を検知して Codex の Completed (e87ccf2) の約 2 分前に終わった。
2. 修正を push して起動し直した watch には、その Completed は前の head のものなので出ない (pr.sh の仕様どおり)。
3. この PR では push で Codex の再レビューが起動しなかった。PR #11 では `New commits` で起動した回がある (canon `facts/github/codex-review-pr-flow`) ので、起動するかは条件による。

Codex は起動すると数秒で summary の Commit 列を head にして Running にする (canon に追記)。これを使い、pr.sh の watch は、Commit 列が head にならないまま 300 秒たつと `@codex review` を 1 回出し、それでも始まらなければ `codex-review not-started` の行を出すようにした (この振り返りと同じブランチ)。手で確かめる手順にはしない。

## 手順と環境

- sandbox で書けなかったもの:
  - `.git/hooks` と `.git/config`。verify.sh の hook の写しの成功経路は手元で実測できていない。失敗経路 (旧版の hook を上書きせず示す) は実物で確かめた。
  - `.git/worktrees/<name>` の削除 (`git worktree remove` が途中で止まる)。
- `gh` は sandbox 内で TLS に失敗するので、PR の作成・merge・ログの取得は sandbox の外で回した。GitHub MCP (`api.githubcopilot.com`) は、このリポへの書き込みが 403 だった。
- 作業ツリーにユーザーの未コミットの変更があったので、scratchpad に linked worktree を作って作業した。common git dir を共有するので、hook の写しは main の作業ツリーにも効く。
- 1 ラウンドの費用: 修正の subagent 1 体 (sonnet、1〜30 分) + レビュー 5〜23 体 (1〜4 分) + verify.sh 約 3 分。Codex は依頼から約 3 分で返した。

## 残っていること

- 各 clone で、common git dir の旧版の hook を一度置き換える: `install -m 755 hooks/pre-push "$(git rev-parse --git-common-dir)/hooks/pre-push"`。それまで verify.sh はその hook を示して落ちる。
- tools の `Makefile` の `check-pre-push-hook` は、まだ `grep PUSH_OK` の判定で、上の表の 1 の問題を持つ。issue #20 の「tools の写しを上流に揃える」として、違えば落とす形に揃える。
- CI と手元で shellcheck の版が違い、手元の緑が CI の緑を意味しない。verify.sh は shellcheck の版を固定していない。
- push で Codex のレビューが起動する条件 (設定か、連続 push の間隔か) は未確認 (canon `facts/github/codex-review-pr-flow`)。
