読者: このリポで次に PR を回す実装セッション (main agent)。前提知識は AGENTS.md と review-perspectives。

## 状況

- PR #21 で、push の後に Codex のレビューが起動せず、watch が約 1 時間待ち続けた。その対策として、`pr.sh watch` に「head のレビューが始まったか」の検査を入れた。
  - Codex の summary の Commit 列が head にならないまま 300 秒たつと `@codex review` を 1 回出し、さらに 300 秒たつと `codex-review not-started` を出す。

- ブランチは 6 commit で、squash merge は `4770f1d`。ローカルレビューは 2 回。Codex は 3 回で、指摘は 2 件、最後の回は指摘なし (👍)。

## 仕様を最初から良くするために

| 仕様 | ラウンド | 最初に足りなかった問い | 次から |
| --- | --- | --- | --- |
| 「この head は要求済みか」 | 3 (ローカルの draft、Codex の draft→ready、Codex の古い head への要求) | 「その事実は、観測できる外部の状態から直接読めるか」(Codex は要求を受けると数秒で summary の Commit 列をその head にして Running にする) | 外部システムの反応を推定する状態 (コメントの流れの時刻から「要求済み」を作る) を持たず、外部システム自身が出す状態 (summary の Commit 列) を読む。自分で持つのは自分の行為 (自分の POST) だけにする |
| 上限明けの要求 | 1 | 「この操作に相手が同じ応答を返し続けたら、何回繰り返すか」 | 外部への要求は、繰り返しの上限を状態で持ってから書く (head ごとに 1 回) |

3 回目の指摘で、要求のコメントを数える機構をやめた (`304399e`)。PR #21 の hook の判定と同じ形だった。推定の材料の次元 (ここでは時刻の前後と head の対応) ごとに外れ、3 回目で機構の種類を変えて止まった。

## 良かったこと

- 設計の前に、Codex の summary の編集履歴 (GraphQL の `userContentEdits`) で「開始時に Running とその commit に書き換える」を実測した。これが検査の前提になり、最後の作り直しも同じ実測に乗った。
- この PR の watch を、ブランチの新しい pr.sh で回した。Codex の環境が無いときは summary が付かず、検査が仕様どおり動かないことを実地で見た。
- 実装 subagent は、毎回の修正で「その修正を戻すとテストが落ちる」ことを固定の列で確かめた。確率的な p5 だけに頼らなかった。

## 手順と環境

- Codex の環境 (chatgpt.com の Codex の environment) がリポに無いと、PR を開いても bot が「create an environment for this repo」とだけコメントし、レビューは来ない。ユーザーに環境を作ってもらうまで止まった (canon `facts/github/codex-review-pr-flow` に追記)。
- `pr.sh watch` の 1 回の起動は、Bash ツールの background の上限 (2 時間) で止まる。止まったら起動し直さず、状態を読んでユーザーに知らせた。
- 1 ラウンドの費用:
  - 修正の subagent (Opus): 12〜80 分
  - ローカルレビュー: 2〜17 体
  - verify.sh: 6〜8 分 (test-pr.ts が約 2 分から約 7 分に伸びた)
  - Codex: push から約 5 分で返した
- サンドボックスでは `.git/worktrees/<name>` を消せない。指定した対象の target-diff.sh が、古い登録で止まった。指定無しで回した。
