追加・変更されたコメントが、その対象の種類で書いてよい内容だけになっているか。

検出手順: diff で追加・変更されたコメントを全て列挙し、各コメントについて、それが注釈するコードを X として次を行う。
1. 対象を分類する。コメントごとに、それが付いた位置で決める。同じファイルの中でも別々に分類する。
   - 自己完結的であるべき対象: 関数・クラス・型とそのメンバー・定数の宣言、スクリプトの先頭、コンテナイメージ、設定ファイル。
   - 自己完結的でない対象: 関数やスクリプトの本体の中の処理、式の中、hunk。
   - 迷ったら後者。
2. 前者なら、書いてよいのは他から辿れない契約だけ: 事前条件 (引数・環境変数・事前に必要な副作用のうち、欠くと正しさやセキュリティの前提が崩れるもの)、責務 (定数なら値の意味)、事後条件・副作用。`--help` があるスクリプトはそれが契約源なので書かず、無いスクリプトは header に呼び出し契約 (入出力・環境変数・引数) を必要最小限書く。語彙が対象のドメインの外に出ていれば単一責任を破っている。
   - 契約かどうかは、コメントを真偽を持つ命題に分解し、各命題 P について「P が偽なら呼び出し側は別の使い方をしてよいか」で決める。よい: 契約。
   - テストの先頭のモデルや、テストのケースの並びの見出しが述べる検査する性質は、そのテストの契約。本体の中にあっても前者として扱う。
   - 契約でない命題は、それが守る本体の中の行を X として 3・4 の問いで制約になるなら、削らずにその行の直前へ移す案を出す。それ以外は削る案を出す。
3. 後者なら、コメント無しで、その言語・一般的なコマンドに精通した読者が X に加える変更 X′ を名指しする (行を消す、簡単な形にする、既定値に戻す)。名指しできなければコメントを削る案を出す。
4. 3 で X′ を名指しできたら、コメントを真偽を持つ命題に分解し、各命題 P について「P が偽なら X を X′ に変えてよいか」を答える。
   - よい: 制約。外部の事実でも同じ。
   - よくない: 帰結・解説。
   - 真偽を持たない: 実況・言い換え。ただし制約が守る X を名指しする節 (「〜ので、既定ブランチを main に固定する」の後半) は数えない。
5. 4 で制約でない命題を全て削り、制約 1 文だけの書き換え案を出す。
   - 制約が特定の相手の観測事実なら、「<固有名の相手> が <実測した挙動> する」の 1 文にする (「X は要求 Y を送り、応答を待つ」)。
   - 制約の根拠 (出典・実測) が非自明なら canon に置き、文の末尾に参照を添える。文は残す。
   - 変更が必要になった経緯は PR 本文に移す。
匂い: コード・名前・処理の言い換え, 自明な既定動作の説明, 消した・移した物の行き先, インストールしたもの・定義したものの使用箇所, hunk の中だけで完結させようとする説明, no longer, has no, 括弧書きの補足, 別ツール・別バージョンの解説, e.g., 複数形の一般化された主語 (servers that ...)
判定規則:
- 外部依存の事実であることは削る理由にならない。canon に移すのは根拠で、文は残す。
- 語形 (「〜ので」「〜ように」「〜ため」、括弧書き) は判定に使わない。匂いは候補を探すためだけに使い、判定は 2 と 4 の問いで行う。理由と行動が 1 文にあっても、理由が制約なら 1 文の制約で、理由の連鎖ではない。
- 「bare clone の HEAD は src の最後の checkout を写すので、既定ブランチを main に固定する」(`git symbolic-ref HEAD refs/heads/main` への注釈): X′ = その行を消す。P = bare clone の HEAD は src の最後の checkout を写す。偽なら (HEAD が常に main なら) 行を消してよいので制約。書き換えは要らない。
- 「無いと一時的な失敗と区別できずに再試行し続けるので、先に確かめる」(`command -v curl` と `jq` の確認への注釈): X′ = 確認を消し、実行時の失敗に任せる。P1 = 無いと一時的な失敗と区別できない。偽なら確認を消してよいので制約。P2 = watch は無限に再試行する。偽でも (再試行に上限があっても) 恒久的な失敗を一時的と誤るので確認は要り、帰結。P2 を削る。
- 「review の編集が changed として検査に入るように、出す対象になる review (本文のある COMMENTED と CHANGES_REQUESTED) を多くする」(生成器の式の中の重みへの注釈): 後者。X′ = 重みを均す。P = 出す対象でない review の編集は changed の検査に入らない。偽なら均してよいので制約。括弧書きは守る X の名指し。
- 「先頭から数えて何件目の要求から失敗させるか」(生成器の式の中の `skip:` への注釈): 後者。真偽を持たないので言い換え。削る。
- テストの先頭の「モデル (pr.sh の先頭の仕様を集合で書いたもの): …」: P = 一時的な失敗を 2 件まで挟んでも結果は変わらないことを検査する。偽なら pr.sh を変える人はその性質を別に確かめなければならず、使い方が変わるので契約。pr.sh の先頭の仕様と重なって見えても、検査する性質はテストの先頭にしか無い。
- 説明を書き足すこと、仕様上必須の振る舞いのコメントを観測事実に書き換えて残すことは解ではない。
