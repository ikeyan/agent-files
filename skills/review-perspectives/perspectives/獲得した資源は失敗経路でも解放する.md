獲得したもの (タイマー、プロセス、リスナ、ハンドル、一時ファイル・一時ディレクトリ、ロック、接続、応答待ちの要求) が、失敗して捨てられる経路でも解放されているか。

検出手順: diff 内で資源を獲得する呼び出し (setTimeout / setInterval、spawn、on / addListener、open、mkdtemp / mktemp、lock、connect、応答待ちの登録 = resolve / reject / timer を Map に置く) を列挙する。それぞれについて、獲得した関数・オブジェクトの全ての出口 (正常 return、例外、早期 return、獲得から try に入るまでの間の例外、相手プロセス・接続の exit / close / error イベント、呼び出し元が失敗と判断してオブジェクトを捨てる箇所) を列挙し、各出口で解放 (clearTimeout、kill、off、close、rm、unlock、reject) が行われるかを答える。特に「相手が終了したとき (初期化・ハンドシェイクの途中で終了した場合を含む)、それ宛てに送って応答待ちの要求とそのタイマーはどう終わるか」を答える。「候補を順に試して失敗したら次へ」の構造では、失敗した候補が獲得したものを列挙する。
匂い: exit / close / error ハンドラが Promise を reject するだけで応答待ちの Map に触れない、初期化の要求と exit を Promise.race で競わせて負けた側を放置する、setTimeout に対する clearTimeout が応答受信の経路にしかない、unref されていないタイマー、catch 節に kill / close / clear が無い、失敗した候補オブジェクトへの参照を持たずに次の候補へ進む、獲得と try の間に文がある、関数末尾だけにある cleanup。
判定規則: 「呼び出し元が最後に process.exit するので実害がない」は是認理由にならない (別の呼び出し元で露見する)。解は、資源を獲得したオブジェクト自身が終了イベントか言語のスコープ終端の仕組み (context manager / `using` / defer / RAII / finally / dispose) で解放する構造を優先し、失敗のたびに呼び出し元が個別に片付ける形は次善。指摘には、解放されない資源と、それが露見する呼び出し元を 1 つ添える。
